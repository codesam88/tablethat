# Brief: OKF compatibility for a task-notes bundle (`.plan/`)

Researched: 2026-11-02 | Versions: OKF v0.1 Draft (frozen snapshot, Jun 2026) + v0.2 (released 2026-07-24, last SPEC revision 2026-08-21); annotated guide okf.md/spec (Jun 2026); tools page checked 2026-10-15 | Overall confidence: high on structural conformance and the v0.2 trust layer (verified against canonical SPEC.md); medium on the field-collision migration strategy (no task-notes-over-OKF precedent found; recommendation is reasoned, not exemplar-backed)

## 1. Baseline

Open Knowledge Format (OKF) is an open format for "knowledge" bundles: a directory tree of markdown files with YAML frontmatter. Each non-reserved `.md` file is a **concept** whose **concept ID** is its file path minus the `.md` suffix (e.g. `tables/orders.md` → `tables/orders`). OKF is deliberately minimal and tool-agnostic: no schema registry, no central authority, no required tooling; `cat` a file to read it, `git clone` to ship it.

**The only hard requirement (conformance):** every non-reserved `.md` file must contain a parseable YAML frontmatter block, and that block must contain a non-empty `type` field. Everything else is soft guidance; consumers MUST NOT reject a bundle for missing optional fields, unknown `type` values, unknown additional keys, broken cross-links, or missing `index.md` files. This permissiveness is intentional — bundles grow, get refactored, get partially generated by agents.

**Reserved filenames** (must NOT be used for concepts, at any level): `index.md` (directory listing, normally no frontmatter) and `log.md` (dated update history). All other `.md` files are concepts.

**Recommended (not required) frontmatter:** `title` (display name), `description` (one-line summary), `resource` (URI of the underlying asset), `tags` (YAML list), and a timestamp. v0.1 used `timestamp` (ISO 8601). v0.2 supersedes it with `generated: { by, at }` (legacy `timestamp` stays readable; prefer `generated.at` when updating).

**v0.2 trust/lifecycle layer (all optional):** `sources` (provenance, with per-source credibility signals `author`/`usage_count`/`last_modified` and a `usage_window` sibling), `generated`, `verified` (list of `{ by, at }`; a bare mapping counts as a one-element list), `status` (`draft`/`stable`/`deprecated`; absent ⇒ `stable`), and `stale_after` (absolute instant; stale when `now >= stale_after`). Also one prescribed concept type: `Attested Computation` (carries `runtime`, `parameters`, `computation`, `executor`, `attester`). `okf_version: "0.2"` may appear in the frontmatter of a bundle-root `index.md` (the only place frontmatter is allowed in an `index.md`).

**Links:** standard markdown. Absolute bundle-relative form `/path/to.md` is recommended (stable under moves); relative paths also work. Consumers MUST tolerate broken links (a not-yet-written target is not malformed).

**Index files:** no frontmatter (except root `okf_version`); body sections group concepts as `* [Title](file.md) - description`. **Log files:** flat date-grouped list, newest first, headings `## YYYY-MM-DD`.

**Actors:** `generated.by`/`verified[].by` use `<producer>/<version>` (agents/tools), `human:<id>` (people), `process:<id>` (automation). Trust tiers derive from `verified`: none ⇒ unverified; only non-`human:` ⇒ machine-confirmed; any `human:` ⇒ human-reviewed.

**Conformance is version-agnostic:** a v0.1 bundle is consumable by a v0.2 consumer via the fallbacks above. Consumers that don't understand a declared version attempt best-effort consumption rather than refusing.

## 2. What research adds

**Corrections and updates (common prior beliefs that are wrong or outdated):**

- "OKF requires a central schema/registry or governance." False. There is no schema registry and no central authority; type values are not registered centrally. Producers pick descriptive values; consumers tolerate unknown types.
- "`timestamp` is the canonical freshness field." Outdated as of v0.2 (released 2026-07-24). Prefer `generated.at`; legacy `timestamp` stays readable. Do not emit new `timestamp`-only freshness in new work.
- "Citations live in a `# Citations` body section." Superseded in v0.2 by the frontmatter `sources` family. Consumers still parse a legacy `# Citations` list for v0.1 docs, so don't delete them, but new provenance belongs in `sources`.
- "`index.md` may carry frontmatter." False except for the root `index.md`'s `okf_version`. Subdirectory `index.md` files have no frontmatter.
- "OKF's `status` field means task lifecycle." No — OKF `status` is `draft`/`stable`/`deprecated` (document lifecycle). A task's "open/in-progress/done" is a different vocabulary that happens to share the key name.

**Practices, constraints, techniques:**

- Reserved-file exclusion is mandatory in any listing logic: any code that enumerates `.md` files must skip `index.md` and `log.md` (they are not concepts). Otherwise an OKF bundle dropped into the directory is mis-parsed as concepts and fails (no frontmatter / missing `type`).
- Unknown-key tolerance must be real, not nominal: consumers (and linters) must preserve round-trip unknown keys and must not reject documents carrying OKF-recommended or trust fields. A schema with `additionalProperties: false` breaks OKF compat the moment someone adds `title` or `generated`.
- Type values are free-form and domain-specific; there is no fixed list. A task-notes bundle may legitimately use `type` values like `Task`, `Bug`, `Decision`. (See collision analysis below.)
- Links should use bundle-relative `/path/to.md` form to participate in OKF graph tooling; broken links are explicitly allowed, so referencing a not-yet-created task is fine.
- For agent-generated notes, populate `generated: { by, at }` (with an explicit UTC offset, e.g. `...Z`). For human-verified notes, add `verified: { by: human:<id>, at }`. `status` and `stale_after` are optional trust signals, never validation errors.
- Body structure matters for retrieval: prefer headings/tables/code blocks; conventional headings include `# Schema`, `# Examples`, `# Computation` (v0.2), and `# Citations` (legacy).

**Pitfalls and failure modes:**

- **`type` collision (plan kind-of-work vs OKF concept type).** Plan's `type` holds kind-of-work (`bug`/`feature`/`chore`/...); OKF's `type` holds concept type (`BigQuery Table`, `Task`, ...). These are different semantics sharing one key. *Migration options:* (a) rename plan's field to a non-colliding key (e.g. `kind`) — clean OKF semantics but breaks every existing task file, schema, validator, formatter, and user habit (large blast radius, needs a migration); (b) keep plan's `type` as-is — structurally conformant (it is non-empty) and external tools tolerate it, but they will label a task's concept type as "bug"/"feature", which is misleading; (c) keep plan's `type` AND add a separate OKF-facing key (e.g. `concept_type`) — two sources of truth, avoid unless needed. No task-notes-over-OKF precedent exists in the ecosystem (lead: reasoned from the spec, not exemplar-backed).
- **`status` collision (task lifecycle vs OKF document lifecycle).** Plan's `status` (`idea`/`backlog`/`open`/`in-progress`/`blocked`/`done`) vs OKF's `status` (`draft`/`stable`/`deprecated`). An OKF consumer filtering `status: stable` would hide every task. Risk is interoperability quality, not rejection (values are tolerated).
- **Reserved-file collision with task listing.** If `index.md`/`log.md` are not excluded from listing, a conformant OKF bundle placed in the directory is treated as a (broken) task. Conversely, if excluded, the tooling must not lint/format them as tasks.
- **Flat vs nested.** A tool that only lists top-level `.md` files (no recursion) will not see OKF concepts nested in subdirectories. They remain valid OKF but invisible to that tool. Don't add recursion unless the tool is meant to own the whole bundle.
- **Slug charset can be stricter than OKF.** A slug rule such as `^[a-z0-9]+(?:-[a-z0-9]+)*$` rejects uppercase, underscores, dots, and spaces. OKF imposes no filename restriction. The tool is then a subset; external concepts with other filenames won't be managed. Document as a boundary; don't loosen without reason.
- **Timestamps need an explicit UTC offset in v0.2** (e.g. `2026-06-30T14:00:00Z`). Any emitter adding `generated.at`/`verified[].at`/`stale_after` must include the offset; bare local datetimes are non-conformant.
- **Empty/missing `type`.** Conformance fails only on missing or empty `type`. The tool's required-field validation should already cover this — confirm it is enforced, not just schema-declared.

**Alternatives and trade-offs, including when NOT to conform:**

| Approach | Cost | OKF semantics | Breaks existing users? | When to use |
|---|---|---|---|---|
| Rename plan fields (`type`→`kind`, `status`→`state`) | L | Clean | Yes (migration needed) | Only if the bundle must be first-class OKF with no semantic overlap |
| Keep plan fields; document overlaps as a profile | S | Structural only | No | **Recommended** for "never locked in" goals — smallest change, external tools tolerate the values |
| Keep plan fields + add OKF-facing alias key | M | Split truth | No | Only if a consumer needs OKF-native typing without migration |
| Don't conform at all | 0 | None | No | Private plan-only bundles never consumed by external OKF tooling; also if strict slug/validation guarantees must be preserved |

**Recommended approach:** structural conformance (keep plan's field names), plus reserved-file exclusion, schema relaxation for OKF keys, pass-through of unknown keys in the formatter, optional trust fields, and a documented profile note describing the two semantic overlaps. Reasoning: OKF conformance is intentionally minimal and permissive; plan already satisfies rules 1–2 (frontmatter + non-empty `type`); the smallest change achieves "external tooling works" without breaking existing users, which aligns with "users are never locked in to plan." Do not rename unless a concrete external consumer requires OKF-native `type`/`status` vocabularies.

## 3. Worker checklist

Things to confirm in this codebase before changing anything:

- `src/plan/store.rs` — `read_task_files` and `sorted_md_entries` are flat (`read_dir`, no recursion) and exclude only `.TEMPLATE.md`. Confirm: add `index.md` and `log.md` to the exclusion set; decide whether to recurse (recommend: stay flat, document).
- `src/plan/store.rs` — `init_plan` writes `.schema.json` + `.TEMPLATE.md` only. Confirm whether to also seed an `index.md` (optional per OKF; recommend: no, or a minimal one — decide explicitly).
- `src/plan/lint.rs` — `validate_all` treats any key not in `required`/`properties` as an unknown-key warning, and `.plan/.schema.json` sets `additionalProperties: false`. Confirm: relax to allow OKF-recommended (`title`, `description`, `resource`, `tags`, `timestamp`) and trust (`sources`, `generated`, `verified`, `status`, `stale_after`, `okf_version`) keys without warnings; or set `additionalProperties: true`.
- `src/plan/lint.rs` — conformance check must stay version-agnostic: validate only "parseable frontmatter + non-empty `type`", never require v0.2-specific fields. Confirm no v0.2 field is made required.
- `src/plan/format.rs` — `normalize_frontmatter` preserves unknown keys after the canonical order (`status`, `type`, `priority`, `area`). Confirm: OKF keys survive a format pass; consider whether any should join `CANONICAL_ORDER` (recommend: no, keep plan's canonical order; OKF keys pass through).
- `src/plan/model.rs` — `Task` parses only `status`/`type`/`priority`/`area`. Confirm: OKF fields are safely ignored (they are, since only declared fields are deserialized); if surfacing them is wanted, add optional fields deliberately.
- `src/plan/store.rs` — `is_valid_slug` is stricter than OKF's filename rule. Confirm: document as a boundary; do not loosen without a reason.
- Task bodies — check for cross-references; if any, confirm they use bundle-relative `/...md` form (recommended) rather than relative paths, so OKF graph tooling can resolve them.
- `tests/` (e.g. `tests/cli_e2e.rs`) — confirm no test assumes `index.md`/`log.md` are tasks, and no test asserts `additionalProperties: false` rejects OKF keys.
- Links in `.plan/*.md` — verify none currently collide with reserved names (none do today; confirm after any OKF bundle is added).
